---
description: Compile the as-built record of an implemented plan — what shipped vs the plan, every decision and its why, the data flow, a reviewer's guide — as a dated, frozen canvas nested under the plan canvas
argument-hint: "[documentId] [base..head] — omit the id to use this session's plan canvas; omit the range for the current branch's changes"
---

Compile an **as-built record** for a plan that has been implemented, as a nested canvas under the plan canvas on Unpaged, using the `unpaged` MCP tools, then give the user the link. Follow these instructions exactly.

An as-built record is the reviewer's map of what actually shipped: each plan item's outcome, every decision with its why and where that why comes from, the runtime flow that changed, and the order to read the code in. It is written once, dated, and never edited afterwards; a plan implemented in several rounds gets several records, and the chain of them is the plan's history.

## Input

- **The plan canvas.** If the first token of `$ARGUMENTS` is a document id — the **whole** token matches `[A-Za-z0-9_-]{8,128}` and holds no `..` — that is the plan canvas. A token carrying `..` is a git range, never an id: `/unpaged:as-built production..HEAD` records this session's plan canvas over that range. A bare ref that would also pass as an id is read as the id, so pass it as a range instead — `mybranch..HEAD`, not `mybranch`. Otherwise use the plan canvas this session created or updated with `/unpaged:visual-plan`. With neither, say *"No plan canvas in this session — pass its id: `/unpaged:as-built <documentId>`"* and stop.
- **The change.** If `$ARGUMENTS` carries a git range (`base..head`, or a single ref meaning `ref..HEAD`), that is the change. Otherwise it is `merge-base(<default branch>, HEAD)..HEAD`, where the default branch is what `git symbolic-ref refs/remotes/origin/HEAD` names, falling back to `main`. If the range holds no commits, say *"Nothing to record: the range is empty"* and stop.
- **The pull request**, when `gh` is on the `PATH` and `gh pr view --json number,url,title,body,baseRefName,state` succeeds for the current branch: its number and URL go on the stamp, its title and body are input for the summary, and when `state` is `"OPEN"` step 7 refreshes its bounded Unpaged preview section. No PR is fine.

Every shell step in this command is **read-only** (`git log`, `git diff`, `git show`, `gh pr view`), with one exception when an open pull request exists for the current branch: step 7 updates only the bounded `<!-- unpaged-plan:start --> ... <!-- unpaged-plan:end -->` preview section of that pull request's description via `gh pr edit --body-file` using a temporary file outside the repository. This command never commits, pushes, or edits repository files.

## Preconditions

The `unpaged` MCP server ships with this plugin. If its tools (e.g. `node_create_with_elements`) are missing or return an authentication error, tell the user to run `/mcp` (or open **Customize → Installed** and choose **Sign in** on **unpaged** in the GitHub Copilot app), authenticate the **unpaged** server, and re-run `/unpaged:as-built`. Do not fall back to a Markdown file or a chat summary.

## Read

1. **The plan.** `document_get(documentId)` gives every node and element: the root node (`rootNodeId`), the status stamp (the root's `text` element whose content starts with `**Status:**`), the phase links (the root `rectangle`s with `isLink`, in `linkOrder`, whose target node holds a plan task `checklist` — never the `📝 Decision log` box, never a `📐 As built · …` box an earlier run added, and never optional `Context · …` / `Decisions · …` reference canvases that hold no task checklist), the phase nodes they link to and their `checklist` items (the plan's tasks, each with a stable item id), the Decision log node (title starts with `📝 Decision log`) and its table(s), and any earlier as-built nodes (title starts with `📐 As built`). A small single-phase plan has no phase node and no phase box: `/unpaged:visual-plan` puts its `checklist` on the root instead, and then the root's checklist items are the plan's tasks — one phase, with no box to label in step 5. A canvas whose tasks you find in neither place has no plan to reconcile: say *"No plan tasks on that canvas"* and stop, rather than recording every change as added work and stamping the plan BUILT.
2. **The decision log rows**: every row of every table on the Decision log node except the header row. A plan rendered by an older plugin has no such node; then every why below is reconstructed.
3. **The code.** `git log --no-merges --format='%h %s' <range>`, `git diff --stat <range>`, `git diff --name-status <range>`, then the diffs themselves (`git diff <range> -- <path>`) for every file that matters to a reviewer — enough to describe honestly what changed and how the pieces call each other. Read before you write: a file you did not read is described as *not read*, never guessed.

## Reconcile

- **Earlier records come first.** A task that an earlier as-built node on this canvas already carries as ✅ done, 🔀 changed or ⛔ dropped keeps that outcome; its Why cell says *shipped in 📐 As built · <that date>* — or, for a dropped task, that record's reason and where it came from — and it is not re-judged: a later round's range does not contain the earlier round's commits, nor its PR. One exception: a dropped task that **this** range implements after all is judged against this range (✅ or 🔀), with *"📐 As built · <that date> recorded it dropped"* in its Why cell — a later round can add back what an earlier one set aside, and the record says so. Only tasks no earlier record resolved are otherwise judged against this range.
- **Each remaining plan task gets one outcome**: ✅ done (shipped as planned), 🔀 changed (shipped, but not as the plan said), ⛔ dropped (nothing in the range implements it **and** a Decision log row, the plan or the PR says it is not being done — a dropped task always has a stated reason), or ⏳ open (nothing in the range implements it and nothing says it was dropped). Work in the diff that no plan item covers is ➕ added. Judge by the diff and the commits, not by the checklist's ticks. A phase follows its tasks: ✅ when all are done, 🔀 when any is changed or dropped, ⛔ when all are dropped, ⏳ when any is open.
- **Every why carries its provenance**, in the cell itself:
  - `📝 recorded` — a Decision log row covers it: carry that row's why and alternative, in the row's own words.
  - `🔍 reconstructed` — no row covers it and you infer the reason from the diff, the commit messages, or the PR body: write *"inferred: …"* so the reader knows it is your reading, not the author's.
  - `not recorded` — no row and nothing to infer from. Write exactly that. Never fill the gap with a plausible reason, and never present a reconstructed why as recorded.
  Count the three kinds; the finish line reports them.
- **Data flow** is drawn only when the change alters a runtime flow — a new call path, a new file other files call into, a changed sequence between components. A copy change, a doc change, or a refactor that keeps every call path is *"No runtime flow changed"* in the summary, with no diagram.
- **The plan is complete** when no task is ⏳ open — every task is done, changed, or dropped with its reason, in this record or an earlier one. Otherwise the record is **partial**: say so in its title and summary, and leave the plan's status stamp alone — a plan is stamped BUILT once, when nothing of it is left.

## Build

**Date** is today, `YYYY-MM-DD`. **Title** is `📐 As built · <date>`; a partial record is titled `📐 As built · <date> (partial)`. If a node with that exact title already exists on the plan canvas, append ` (2)`, then ` (3)`, and so on — `📐 As built · <date> (partial) (2)` is a second partial record of the same day. **A re-run never corrects an earlier record** — it adds one, and touches neither the title nor the elements of a record an earlier run wrote. The only later change to a finished record is a correction its owner or editor asks for by comment (*Comments on the record*, below). The record this run is writing is yours until the finish line; steps 1–4 build it in several calls.

1. **The as-built node**, `node_create_with_elements` with `parentNodeId` = the plan's root node, `backgroundColor: "#f6efe3"` (Warm Paper), `canvasWidth: 1920`, `canvasHeight: 1620` (taller when tables need room, never overlapping), and a 1–2 sentence plain-English `content` summary. Prose cells need width: the two tables run the full canvas width (`x: 60`, `width: 1800`), stacked below the Summary and Follow-ups cards:
   - Header: uppercase eyebrow (`AS-BUILT RECORD` in `#786554` Inter 12 bold) + title `text` top-left: `## 📐 As built · <date> — <plan title>` (`Outfit, sans-serif`, fontSize 28 bold `#3b2a1e`).
   - Stamp pill top-right (`#efe6d6`, `#cbb99f` border, `cornerRadius: 16`) holding `text` with exact shape: `**As built:** <date> · [PR #<n>](<url>) · <base>..<head> · frozen` (`Inter` 13 `#3b2a1e`) — omit the PR part when there is none; `<base>..<head>` are short SHAs.
   - **Summary** card (sage tint `#f4f9f5`, `#c3decb` border, `#2f7d57` 4px left accent bar, `cornerRadius: 12`, `x: 60, y: 120, width: 880, height: 170` — no `uml-note`): `SUMMARY` eyebrow + at most five sentences covering what shipped, the largest deviation from the plan, whether a runtime flow changed, and — for a partial record — what remains.
   - **Follow-ups** card (amber tint `#fdf6ea`, `#e6cfa8` border, `#c26a1b` 4px left accent bar, `cornerRadius: 12`, `x: 970, y: 120, width: 570, height: 170`): `FOLLOW-UPS & GAPS` eyebrow + what is left, known gaps, and every *not recorded* why — the author fills those in by commenting on the row.
   - **Plan delta** `table` (`x: 60, y: 320, width: 1800`, ~48 px per data row + ~46 px header, `backgroundColor: "#fffaf1"`, `borderColor: "#d6c7b0"`, `textColor: "#3b2a1e"`, `fontFamily: "Inter, sans-serif"`, `fontSize: 13`, `textAlign: "left"`, `verticalAlign: "top"`, `columnWidths: [28, 12, 60]`), columns `**Plan item**` | `**Outcome**` | `**Why**`, one row per plan task in plan order, phase headings as rows when it helps, then the ➕ added rows. At most 20 rows; when the plan has more tasks, one row per phase with its tasks folded into the Why cell.
   - **Decisions** `table` (below the plan delta, `x: 60, width: 1800`, ~56 px per data row + ~46 px header, same Warm Paper table styling, `columnWidths: [12, 26, 28, 22, 12]`), columns `**When**` | `**Decision**` | `**Why**` | `**Alternative rejected**` | `**Source**`: every Decision log row (source `📝 recorded`), then the reconstructed decisions a reviewer needs to know about (source `🔍 reconstructed`). At most 20 rows per table; more go to a second table beneath, and the canvas grows to fit.
   - If the server refuses `columnWidths` (an older Unpaged server), retry the call without `columnWidths` and carry on.
   - The navigation link cards come in step 4, once the child nodes exist.
2. **The Reviewer guide node**, `node_create_with_elements` with `parentNodeId` = the as-built node, `backgroundColor: "#f6efe3"`, `1920×1080` (taller if needed), plain-English `content`:
   - Header (`Outfit` 26 bold `#3b2a1e`) + grouped top-right walking pills: link `1` `← As built` (`linkTarget` = as-built node, `#e6effc` / `#1d4ed8`), link `2` `← Plan overview` (`linkTarget` = root node, `#efe6d6` / `#cbb99f`).
   - **Reading order** `table` (Warm Paper table styling, `columnWidths: [36, 64]`), columns `**File**` | `**Why start here**`: the files in the order a reviewer should open them, one line each on what to look for. At most 15 rows.
   - **Seams and risks** card (amber tint `#fdf6ea`, `#e6cfa8` border, `#c26a1b` 4px left bar — no `uml-note`): which existing seams the change touches, where the risk concentrates, and what the author is unsure about.
   - **Test map** `table` (Warm Paper table styling, `columnWidths: [22, 44, 34]`), columns `**Area**` | `**Covered by**` | `**Not covered**`: what the changed behaviour is tested by, and what is not tested at all — say so plainly.
3. **The Data flow node** (only when a runtime flow changed), `node_create_with_elements` with `parentNodeId` = the as-built node, `backgroundColor: "#f6efe3"`, plain-English `content`, header + grouped top-right `← As built` (link `1`) and `← Plan overview` (link `2`) pills, and one `text` element (`x: 60, y: 120, width: 1800`) holding a fenced ```` ```mermaid ```` flowchart: `flowchart TB` with two subgraphs, `Before` and `After`, each declaring `direction LR` so the two flows read as rows, one above the other (a left-to-right chart with subgraphs stacks their nodes vertically and runs past the fold). Keep ~900 px of vertical room below the element — the rendered diagram grows it. Quote every node label, and keep `@` and `?` out of labels: either breaks the parser and the raw code renders instead.
4. **The navigation link cards on the record**, `batch_create_elements` on the as-built node, now that their targets exist (grouped via `group`, top-right `48×48` corner clear for live badges, created in strict `1`–`3` link order):
   - Link `1`: grouped `🔍 Reviewer guide` card (`x: 1570, y: 120, width: 290, height: 76`, `#fffaf1` fill, `#1d4ed8` stroke `2`, `cornerRadius: 12`, top-level `isLink: true` and `linkTarget` = the node of step 2).
   - Link `2` (only when a Data flow node was created): grouped `🔀 Data flow` card (`x: 1570, y: 214, width: 290, height: 76`, `#fffaf1` fill, `#1d4ed8` stroke `2`, `cornerRadius: 12`, `isLink: true`, `linkTarget` = the node of step 3).
   - Last link: compact grouped `← Plan overview` pill (`#efe6d6`, `#cbb99f` border, `isLink: true`, `linkTarget` = plan root) placed cleanly beside the stamp or below the cards so reviewers can jump straight back to the plan.
   Then look at the record before stamping anything: `node_picture({ documentId, nodeId })` for the as-built node and for the Reviewer guide node, and fix what the picture shows — a table cell cut off by its row, a card whose text runs past its edge, boxes that overlap — through the MCP tools (taller rows and canvas with `element_update` and `node_update`), then look again, at most twice per canvas. The Data flow canvas holds a Mermaid fence, which the picture draws as a grey placeholder, so it is not checked this way. If `node_picture` is missing (an older server), skip the look and say so in your reply. `isLink` and `linkTarget` are top-level fields of the element, next to `type`, not entries of `properties`.
5. **Stamp the plan** (only these edits to the plan's own content, and only as far as the bullets below allow — the ticks always run; the status stamp and the phase labels only when this record completes the plan):
   - The root's status stamp: `element_update` on the `**Status:**` text with `changes: { properties: { text: "**Status:** ✅ BUILT" } }` and the `expectedRevision` from your read.
   - Each phase card's label: prefix its phase title with the phase's outcome — ✅ (every task done), 🔀 (a task changed or dropped), or ⛔ (every task dropped) — `element_update` with `expectedRevision`, touching nothing else. If the linked phase `rectangle` carries its own `text` label (single-element box), prefix `rectangle.properties.text`; if it has empty `text` and belongs to a `groupId` (Warm Paper grouped phase card), prefix the phase title `text` element in that same `groupId`. On a plan already stamped `✅ BUILT`, skip the stamp and the phase labels, and never prefix a label that already starts with ✅, 🔀 or ⛔ — the plan is stamped and labelled by the first complete record, and a later one leaves it as it is — but still tick below, so a task a later round adds back is checked off when it ships.
   - Each done or changed task: `checklist_toggle_item` with `checked: true` (dropped tasks stay unchecked).
   For a partial record, tick the done tasks and leave the stamp and the phase labels alone.
6. **Link the record from the root**: a clickable `📐 As built · <date>` link card (with `(partial)` or `(2)` when the title has it; styled in Warm Paper `#fffaf1` with `#1d4ed8` stroke `1.5` on `#f6efe3` roots, or matching the existing root palette on older white roots) linking to the as-built node, placed on the bottom scaffolding dock row right of `📝 Decision log`; the next record goes right of the previous one. A canvas rendered by an older plugin has no Decision log box: start the row below everything already on the root — the phase boxes, whether they run left-to-right or top-down, and the goal note — so a record never reads as a phase. Make room with `node_update` before placing a box that would not fit: `canvasWidth` when the row reaches the root's right edge, `canvasHeight` when the row itself falls below its bottom. A record box never sits outside the canvas and never overlaps an element already on it.
7. **Refresh the pull request preview**, when *Input* found an open pull request (`state: "OPEN"`) for the current branch: call `document_update({ documentId, isPublic: true })` on the `unpaged` server so the plan is public and the server re-renders the updated root canvas preview (with its `✅ BUILT` stamp and link to this record). Anyone with the plan's link can then read it without an account, and copy it once signed in. The plan's public link `<url>` is the one the reply gives; when the reply gives none, it is `<web app>/share/<documentId>`, where `<web app>` is the web app address the `unpaged` server's instructions name (`https://unpaged.io` for `mcp.unpaged.io`). If the call is refused (only the plan's owner can make it public), skip this step, leave the pull request description unchanged and say why in one sentence. Splice ONLY the standalone bounded `<!-- unpaged-plan:start --> ... <!-- unpaged-plan:end -->` section into the pull request's `body` (ignoring any markers inside inline code or fenced code blocks, and never passing a canvas title on a shell command line): when `node` is on `PATH`, run `gh pr view "<prUrl>" --json body --jq .body > "<inFile>" && node "${CLAUDE_PLUGIN_ROOT}/monitors/plans.mjs" splice "<url>" < "<inFile>" > "<outFile>" && gh pr edit "<prUrl>" --body-file "<outFile>"` using temporary files outside the repository and deleting both afterwards — if `plans.mjs splice` exits non-zero, leave the pull request description unchanged, delete the temporary files, and report in one sentence the reason `plans.mjs splice` printed on stderr (never splice by hand after `plans.mjs splice` refused). Only when `node` is not on `PATH`, replace a single existing standalone bounded block (`### Visual plan`, `[![Visual plan](<url>/preview.png?v=<unix-seconds>)](<url>)`, `[Open visual plan on Unpaged (no account needed)](<url>)`) or append one with a fresh `?v=<unix-seconds>` cache-buster while preserving all surrounding PR description text via `gh pr edit "<prUrl>" --body-file "<tmpfile>"` (leaving the description unchanged if existing marker lines are unpaired or duplicated). If `gh pr edit` is declined, skip and note that in one sentence in your reply. When the section was updated, say in one sentence that the plan is public — anyone with the link can read it without an account — and that **Share → Public link** in Unpaged turns that off.

**Element rules** (the render breaks otherwise): on a `text` element `fillColor` is the text colour — use Warm Paper inks (`#3b2a1e`, `#4a3a2d`, `#786554`, `#1d4ed8`, `#226142`, `#9a4e10`), never white on light cards; give every `rectangle` (and any other basic shape: `triangle`, `diamond`, `hexagon`, `ellipse`, `block-arrow`) both a `fillColor` and a `strokeColor` — older servers refuse a basic shape that lacks either, and the whole batch with it; use Warm Paper structured cards instead of `uml-note` sticky notes; tables hold at most 20 rows; keep every element inside its canvas and nothing overlapping; cells and cards are CommonMark Markdown, one idea per cell, no code pasted — a path or an identifier in backticks is the most code a cell carries.

If a permission classifier refuses one of several create calls while its siblings succeed, retry that one call once before reporting anything.

## Finish

Reply to the user with:
- The link: `https://unpaged.io/document/<documentId>/edit?nodeId=<asBuiltNodeId>` — call it a canvas (or whiteboard), never a board.
- One line of counts: plan items done / changed / dropped / open / added, and whys recorded / reconstructed / not recorded.
- One line on the plan: *"The plan canvas is stamped BUILT"*, or for a partial record *"The plan canvas keeps its status, <status> — <k> tasks are still open"*, where `<status>` is the stamp you read in step 1 and never an assumption: a canvas rendered in another session may still read 📋 PROPOSED, and one an earlier record completed reads ✅ BUILT.
- If a Data flow node was created: *"Open the Data flow canvas once in edit mode so viewers see the diagram rather than its source."*
- Listener status, said truthfully. When the tool `mcp__unpaged__listen_status` is listed (the plugin's mod, which listens to every canvas the session creates or changes, so to the plan canvas once the record is built), report the plan canvas's state from that call: connected → *"I'm listening on this canvas — comment @agent on the record and I reply there."*; connecting or reconnecting → say it is starting or reconnecting; absent or stopped → the *not armed* line below. Without that tool: if this session holds a Monitor on the plan canvas (armed by `/unpaged:visual-plan` or `/unpaged:listen`) and `keys.mjs alive <documentId>` confirms `monitor:connected` after an authenticated poll, *"I'm listening on this canvas — comment @agent on the record and I reply there."* Otherwise *"Push isn't armed for this canvas in this session — run `/unpaged:listen arm <documentId>`."* A Monitor that is starting or reconnecting must be described that way; process creation alone is not listening proof.

## Comments on the record

`@agent` comments on the as-built canvas reach the session through the plan canvas's listener and follow the protocol in `/unpaged:visual-plan`: act only with the unpaged tools on that document, reply in the thread, leave it open; a viewer's request gets an answer, not a change. On the record itself, an owner or editor may ask you to correct a factual error in a cell or a note — do that, and reply with what changed. Never rewrite a `📝 recorded` why (the log row is the author's), never delete a row, and never turn a `🔍 reconstructed` or *not recorded* why into a recorded one yourself: when the author supplies the real reason in a comment, put it in the cell prefixed `📝 recorded (comment, <date>)`.
